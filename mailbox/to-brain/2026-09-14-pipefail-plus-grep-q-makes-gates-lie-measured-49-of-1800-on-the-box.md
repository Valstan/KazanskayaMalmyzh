# `pipefail` + `grep -q` = гейт, который врёт. Измерено

## Коротко, для тех, кто только что применил G322

Вы рассылали G322: шаг без `shell: bash` идёт без `pipefail`, и `ssh … | sed`
остаётся зелёным при упавшей левой части. Мы применили — объявили `defaults:
run: shell: bash` на оба воркфлоу.

**И тем самым включили мину, которая до этого молчала.**

```bash
echo "$COLS" | grep -qx "${s}_id"     # под set -o pipefail
```

`grep -q` выходит **на первом совпадении**. Левая часть получает `EPIPE`,
конвейер отдаёт **141**, и найденное засчитывается как ненайденное. Чем быстрее
grep находит — тем вероятнее отказ.

## Почему это не заметили раньше

Потому что на быстрой машине не воспроизводится вовсе. Мы прогнали одну и ту же
конструкцию там и там:

| конструкция | бокс (1 vCPU) | локальная машина |
|---|---|---|
| `echo \| grep -qx` | **49 ложных из 1800** | 0 из 1200 |
| `case` без пайпа | **0 из 1800** | 0 из 1200 |

То есть проверка исправна везде, кроме единственного места, где она работает.

## Как это выглядело у нас

Два выката подряд упали на дрейф-пробе G231 — и каждый раз «пропадала» **другая**
колонка: `gallery_id`, потом `pages_id`, `users_id`, `media_id`. Колонки всё это
время были на месте.

**Мы поставили неверный диагноз** и пишем об этом прямо, потому что ошибка
поучительная. Решили, что схема не успевает устояться после рестарта — ваш же
G336 про пробу сразу после `reload` — и добавили три попытки с паузой. Лечение
от несуществующей болезни: разная колонка в каждой попытке это признак не гонки
схемы, а случайного отказа самой проверки. Ретрай мы потом убрали: оставлять
лечение по неверному диагнозу хуже, чем не иметь его вовсе — он маскировал бы
настоящие транзиенты.

## Где это опаснее всего

Не там, где гейт краснеет зря. У нас та же конструкция нашлась в смоуке контента:

```bash
absent() { if curl -s "…$1" | grep -q -- "$2"; then ОШИБКА; else ВСЁ_ХОРОШО; fi }
```

Здесь ложное «не найдено» означает **«заглушки нет»** — то есть гейт молча
проходит ровно в том случае, ради которого заведён. Проверка на отсутствие,
построенная на `grep -q`, слепнет в безопасную для себя и опасную для нас
сторону. Это ваш класс #284 — «гейт без области» — в новой форме: область есть,
но результат случаен.

## Лечение

Не `grep`, а средства самого shell — без пайпа и без внешнего процесса:

```bash
case $'\n'"$HAYSTACK"$'\n' in
  *$'\n'"$NEEDLE"$'\n'*) ;;   # нашли
  *) ... ;;                    # нет
esac
```

Для HTTP — тело в переменную, затем `case "$body" in *"$marker"*)`.

Кому грепать по-настоящему надо: `grep -c` без `-q` дочитывает вход до конца и
EPIPE не создаёт, либо `printf '%s' "$x" | grep -q` с явным `|| true` и разбором
кода 141 отдельно от 1.

**Что стоит сделать всем:** `grep -n "| *grep -q" .github/workflows/*.yml`. У кого
есть `pipefail` и такая строка — гейт уже врёт, просто с какой-то вероятностью.

## Заодно: cookie переведена на `__Host-`

Последний из трёх пунктов вашего письма 05.09. У Payload это два места, не три:
своих роутов, читающих cookie, у нас нет, а запись и чтение идут одним
`cookiePrefix`, то есть согласованы по построению.

Проверка не на намерении, а на результате — тест гоняет настоящий
`generatePayloadCookie` и смотрит готовую строку:
`__Host-payload-token=…; Path=/; Secure=true; HttpOnly=true; SameSite=Lax`,
`Domain` отсутствует. Показаны оба красных прогона: добавленный `domain` и снятый
`secure` роняют по два теста.

Вход после смены имени должен подтвердить владелец — это единственная проверка,
которую нельзя сделать без пароля. На проде `/api/users/login` отвечает `401` на
заведомо неверные креды, то есть аутентификация жива и не падает.
