# Проба снята: форма верная. Ваш деплой красный из-за нашего гейта, а не из-за пилота

**ОДНОЙ СТРОКОЙ:** `форма чтения подтверждена — GET /api/secrets?key=… → 200, key_present: true (прогон 42177946727 с main)`; `красный деплой 06.11 — наш ложный G231 (искали visitor-facts_id вместо visitor_facts_id), сайт жив, схема на проде есть, правка гейта в PR`.

## 1. Проба формы — коды сняты

Прогон `42177946727`, workflow `karman-grant.yml`, ref `main`, после влития PR #124 (пути от `VAULT`, без двойного префикса):

| вызов | код |
|---|---|
| `GET /grants?pending=1` | 200 |
| `POST /grants/16/accept` | **409** (уже принят — наш шаг это больше не роняет) |
| `GET /api/secrets?key=ESA_CLIENT_SECRET_KAZANSKAYA` | **200**, `key_present: true` |
| `GET` корень комнаты | 200, `key_present: true` |
| `GET /grants` | 200 |

**Форма чтения — рабочая, секрет читается.** `GET /openapi.json` → 404 — это не наша ошибка сборки пути: схема OpenAPI по корню API не опубликована вовсе (`/api/secrets/openapi.json` давал 404 и раньше). Для чтения секрета она не нужна.

**ADR-0006 держится:** в лог прогона попали только имена полей (`"keys": ["secrets"]`, `key_present: true`) и коды; **значения секрета в логе нет** — проверено отдельным поиском по логу прогона (длинных непрозрачных строк нет, единственная — sha коммита). Тело с секретом удаляется `trap`'ом.

Итог по маршруту grant'а: **accept — исполнен 09.10, секрет в комнате, форма чтения — найдена и проверена.**

## 2. Ваш деплой 06.11 06:40Z — красный, но это НАШ гейт

Выкат упал на шаге «Дрейф схемы — колонки блокировок под каждую коллекцию (G231)» с текстом
«в `payload_locked_documents_rels` нет колонок: `visitor-facts_id`». **Это наша проверка сравнивала
сырой slug с дефисом, а Payload так не называет.** Имена объектов в Postgres у Payload
санитизированы: всё, кроме букв и цифр, заменяется на подчёркивание.

Воспроизведено на локальной БД (своя, PostgreSQL 17.11) — миграция, которую генерирует сам Payload,
даёт ровно:

```sql
ALTER TABLE "payload_locked_documents_rels" ADD COLUMN "visitor_facts_id" integer;
CREATE TABLE "visitor_facts" ( ... );
```

То есть **колонка называется `visitor_facts_id`**, а наш гейт искал `visitor-facts_id`. На той же
локальной БД наш шаг в текущем виде даёт ровно ту же ошибку, что и на проде; с исправлением —
проходит, и **отрицательный контроль срабатывает** (коллекция, которой нет в БД, ловится).

**Что с продом (проверено read-only снаружи, без SSH):** сайт жив и отдаёт 200 — `/`, `/profile`,
`/privacy`, `/api/auth/esa/login` → 302 на ЕСА. Схема на проде есть: `push: true` в общем конфиге
Payload синхронизирует её на старте юнита, поэтому после рестарта таблица `visitor_facts` и колонка
`visitor_facts_id` созданы самим Payload. **Пилот не сломан; красным было наше измерение.**

Правка в PR (файл `.github/workflows/deploy-prod.yml`): сравнение по санитизированному имени
(принимается и сырое написание), **плюс новая проверка — таблица самой коллекции**. Таблица коллекции
и есть настоящий признак дрейфа («коллекция в конфиге, таблицы нет»), а её раньше не проверяли вовсе.

## 3. Дыра в пуш-гейте миграций — она позволила этому пройти

Гейт «Migration guard» ловит **только новые ФАЙЛЫ миграций** в последнем коммите
(`git diff --diff-filter=A HEAD~1 HEAD -- 'web/src/migrations/*.ts'`). Коллекция `visitor-facts`
добавлена **без** файла миграции — гейт прошёл молча. Единственным сигналом стал G231, а он стоит
**после** «Ship artifact + restart» (строка 303 против 178): то есть не гейт, а post-mortem-проверка,
которая уже не может остановить выкат — только покрасить его в красный постфактум.

**Это стоит решить, а не залатать:** гейт, который стоит после рестарта юнита, по построению не
защищает прод. Переносить его перед рестартом — отдельная правка с замером, мы её не тянем в этот PR.

## 4. Противоречие в конфиге — решение за владельцем

`web/src/payload.config.ts` содержит `push: true` **безусловно**, а комментарий рядом говорит:
«push автосинхронизирует схему в dev/CI. Прод-миграции — вручную на этапе деплоя (#017)». По коду
автосинхронизация идёт **и на проде** — комментарий и код расходятся. Либо `push` выключается на
проде (и тогда нужна дисциплина миграций и ручной apply), либо гейт миграций и G231 перестают быть
обязательными. Мы ничего из этого не меняли: это решение владельца, и мы его не выбираем молча.

**Миграцию `visitor-facts` в репозиторий мы намеренно НЕ добавляли:** файл миграции в коммите
останавливает деплой пуш-гейтом до ручного применения на проде, а ручное применение требует SSH,
которого на dev-машине нет с 08.10. Схема на проде уже есть (см. п. 2), а SQL миграции под рукой —
добавим по решению владельца вместе с п. 4.
