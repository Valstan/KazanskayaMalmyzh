# Поправка: наше «схема на проде создана самим Payload» было неверно

**ОДНОЙ СТРОКОЙ:** `в предыдущем письме мы написали, что схему на проде создаёт push:true — это НЕВЕРНО: Payload применяет push только вне production, таблицы visitor_facts на проде нет, и мы это теперь чиним (миграция + применение без SSH)`.

## Где мы ошиблись и почему

В письме `2026-11-06-probe-200-and-g231-false-positive.md` мы написали: «схема на проде создана
самим Payload (`push: true` синхронизирует её на старте юнита)». **Это неверно**, и мы это поймали
на следующем же выкате.

В адаптере `@payloadcms/db-postgres` сказано буквально:

```js
// connect.js
// Only push schema if not in production
if (process.env.NODE_ENV !== 'production' && process.env.PAYLOAD_MIGRATING !== 'true' && this.push !== false) {
  await pushDevSchema(this)
}
```

То есть `push: true` в `web/src/payload.config.ts` работает **только в dev/CI** — на проде
`NODE_ENV=production`, и автосинхронизации схемы не происходит. Комментарий в конфиге
(«Прод-миграции — вручную (#017)») был прав; неправы были мы, когда решили, что `push` спасёт.

**Что это значит по существу:**

- На проде **нет** ни таблицы `visitor_facts`, ни колонки `visitor_facts_id` в
  `payload_locked_documents_rels`. Коллекция `visitor-facts` из PR #125 ехала **без файла
  миграции** — а миграция на проде не применяется сама.
- Сайт при этом **жив**: `/` 200, `/profile` 200, `/privacy` 200, `/api/auth/esa/login` 302;
  смоук деплоя прошёл целиком (маркеры из БД на месте). Коллекция читается только
  авторизованным посетителем, поэтому без таблицы страница `/profile` не падает — а вот запись
  факта и его чтение упадут: таблицы нет.
- **Проверка G231 оказалась права по сути** (таблицы коллекций на месте — их нет), и неправа
  только в формулировке: она искала колонку `visitor-facts_id`, а Payload называет её
  `visitor_facts_id`. Наш прежний вывод «ложное срабатывание, всё в порядке» был неверен —
  виновата и формулировка, и наш вывод.

## Что сделано — и что ещё предстоит

1. **Миграция приготовлена тем же инструментом, что и все прежние:**
   `payload migrate:create` дал `web/src/migrations/20261106_075708_visitor_facts.{ts,json}` —
   `CREATE TABLE "visitor_facts" (...)`, `ALTER TABLE "payload_locked_documents_rels" ADD COLUMN
   "visitor_facts_id" integer`, индексы и внешний ключ. Применение отрепетировано на локальной
   БД (PostgreSQL 17.11): миграция проходит, таблица и колонка появляются, `payload_migrations`
   ведёт сам Payload.
2. **Применение миграций без SSH с dev-машины** — новый workflow `migrate-prod.yml`
   (только `workflow_dispatch`, с подтверждением). Он поднимает туннель до БД бокса из раннера
   (ключ деплоя у раннера есть) и зовёт штатный `payload migrate`, поэтому и DDL, и bookkeeping
   делает сам Payload. Ручной характер сохранён (#017: миграции — отдельное действие перед
   выкатом), но больше не нужен `~/.ssh`, которого на dev-машине нет с 08.10.
3. **Пуш-гейт миграций оставлен как есть** — он и требует, чтобы миграция была применена ДО
   выката: выкат, который добавляет файл миграции, будет остановлен, дальше — `migrate-prod.yml`,
   затем `deploy-prod.yml` через `workflow_dispatch` (он гейт обходит, как и задумано).
