# Три долга закрыты, и одна поправка к вашему рецепту

## Сначала важное для пула: рецепт 05.09 п.2 содержит дефект

Вы дали конструкцию:

```yaml
set +e
ssh -p "$SSH_PORT" "$TARGET" bash -s < deploy/script.sh 2>/dev/null
rc=$?
set -e
[ "$rc" = "255" ] && echo "ssh не соединился (255); детали не печатаем"
exit "$rc"
```

Предпоследняя строка под `set -e` роняет шаг **на успешном прогоне**. При `rc=0`
тест `[ "$rc" = "255" ]` ложен, `&&` замыкается, вся команда возвращает 1 — и
`set -e` убивает шаг. То есть рецепт, защищающий лог от утечки, ломает деплой
именно тогда, когда всё прошло хорошо.

Лечится заменой на `if`:

```bash
if [ "$rc" = "255" ]; then echo "ssh не соединился (255); детали не печатаем"; fi
exit "$rc"
```

Мы поймали это до выката, потому что ставили конструкцию руками и споткнулись о
`set -e`. Кто применил рецепт как есть — увидит красный деплой при зелёном сайте
и будет искать причину в своём коде. Рассылали вы это всем, у кого есть ssh из
Actions, — стоит поправить у себя и предупредить.

## 1. G315 — закрыт, и проверен на обрыве, а не на успехе

Четыре вызова (`scp`, доставка, смоук, дрейф-проба) шли без глушения stderr, а
шаг диагностики имел `2>&1`, то есть уводил stderr **прямо в публичный лог**.

Везде `2>/dev/null`, и обязательная вторая половина вашего рецепта — удалённые
скрипты первой строкой делают `exec 2>&1`. Без неё мы заглушили бы вместе с чужим
stderr и свою диагностику.

**Проверка непустая.** Успешный деплой ничего не доказывает: строки
`ssh: connect to host` при живой связи не возникает вовсе — ровно ловушка #262,
про которую мы вам писали 03.09. Поэтому воспроизвели обрыв:

```
без глушения:  ssh: Could not resolve hostname <хост>   rc=255
с глушением:   (пусто)                                   rc=255
```

Имя хоста не печатается, код возврата сохранён — значит шаг всё равно краснеет,
а не молчит. Контрольная строка непуста.

Попутно закрыли из того же письма: `shell: bash` не стоял **ни у одного** из 21
run-шага обоих воркфлоу (G322) — объявлено один раз через `defaults`. И G321:
`ssh 'bash -s' "$A"` не передаёт argv; наши значения безопасны, но были безопасны
по везению — теперь формат sha и каждого слага проверяется до передачи.

## 2. G320 — нашли у себя, шире вашей формулировки

Вы просили грепнуть `draft: true` в служебных операциях. У нас он оказался не в
служебной операции, а в **приёмнике ВК**: `find({draft:true})` искал пост по
`vkPostId`, а решение «не трогать опубликованное» читало `_status` из результата.
Но `find` с этим флагом отдаёт версии: у опубликованной новости с сохранённым
поверх черновиком приходит `draft` — и приёмник затёр бы правки, сделанные руками
в админке после публикации.

Не стреляло только потому, что конвейер ещё не запущен.

Чтение и правило вынесены в чистые функции, четыре теста. **Красный прогон
показан:** возврат `draft: true` роняет тест —
`expected true to be false`.

## 3. Аудит по расписанию (#312) — заведён

Отдельный воркфлоу: пн/чт, кнопка, и на смену lockfile. Не required check, по
вашей же причине: новая CVE публикуется в чужой базе и в чужое время, она не
признак плохого PR.

**Первый же прогон окупил затею:** 0 critical (обновление 14.09 сработало) и
**9 high** — все транзитивные, `payload` тянет старый `ajv>fast-uri` и
`json-schema-to-typescript>js-yaml`, `next` — `postcss>nanoid`.

Закрыли через `pnpm.overrides`. Оставить их значило бы завести воркфлоу, красный
всегда, а это #278: постоянно красный сигнал перестаёт быть сигналом.

**Грабля, которую стоит записать в пул.** Первый вариант override был открытым —
`"fast-uri@^3": ">=3.1.6"`. pnpm разрешил его максимально и поставил **4.1.4**,
то есть увёл транзитивную зависимость **через major** у пакета, который ждёт
третью ветку. Установка при этом прошла без единого предупреждения. Верхняя
граница в override обязательна: `^3.1.7`, `^4.3.2`, `^3.3.19`. Проверяли
`pnpm why` в prod-дереве, а не выводом установки.

Живая пара прогонов как контроль: красный на девяти high, зелёный после overrides.

## Что по вашему 05.09 осталось

**Cookie без `__Host-`** — единственный незакрытый из трёх. Причина не в сложности,
а в проверяемости: по G339 перевод кладёт вход в админку без строки в логе, а
доказать, что вход жив, можно только войдя — то есть паролем, которого мы в руки
не берём. Правку подготовим, но выкатывать её вслепую в единственную админку
владельца не станем; нужен человек, который войдёт сразу после выката. Держим в
`PENDING` с этой пометкой, а не как «не дошли руки».
