# SESSION_LOG — летопись прошлых сессий

История проекта по сессиям. Основной рабочий файл — [`SESSION_HANDOFF.md`](SESSION_HANDOFF.md):
там состояние проды, следующий шаг и блокеры. Этот файл — **только архив**, его читают
по необходимости, а не на каждом старте.

Файл разделён 30.09 по решению владельца D-097 (ADR-0013: локальный реестр больше 50 КБ
раскладывается на «индекс + файл на запись»). До этого `SESSION_HANDOFF.md` весил 58.7 КБ,
из них **80% — эта история**, а живой части было 11.5 КБ. Читать 47 КБ прошедшего на каждом
старте было бессмысленно дорого: агент грузил в контекст то, что уже не влияет на решение.

## Ноу-хау сессии 15

- **`cmd | grep -q` под `pipefail` врёт.** `grep -q` выходит на первом совпадении, левая часть получает EPIPE, конвейер отдаёт 141 — найденное засчитывается как ненайденное. Измерено на боксе: **49 ложных из 1800**, локально 0 из 1200. Опаснее всего в проверке на отсутствие: там ложное «не найдено» означает «заглушки нет», то есть гейт молча проходит ровно в том случае, ради которого заведён. Лечение — `case` без пайпа.
- **Успешный HTTP-ответ ничего не доказывает.** `forgot-password` отвечает `200 Success` и молчит в журнале, когда адреса нет в базе (защита от перебора). Наблюдаемость пришлось брать сбоку — по `reset_password_expiration` в таблице.
- **Пароль приложения Яндекса принадлежит аккаунту, а не адресу.** Сотрудник организации — отдельный аккаунт с другим UID. Симптом обманчив: пароль рабочий, SMTP пускает, но по чужому логину, а отправка от нужного адреса отбивается `550 Sender address rejected`. Диагноз даёт перебор кандидатов-логинов с одним паролем.
- **IMAP отличает неверный пароль от запрета услуги за минуту.** Пускает IMAP и не пускает SMTP — читать надо не свой конфиг, а условия тарифа.
- **DNS-записи, которые держит услуга хостера, не редактируются** — серые строки в панели, клик не открывает форму. Поэтому SPF «не находился».
- **Дважды поставлен неверный диагноз** (гонка схемы вместо SIGPIPE; «сломал forgot-password» вместо смены e-mail владельцем). Оба раза помогало одно: смотреть на состояние в БД, а не на код ответа и не на свой последний коммит.

## Ноу-хау сессии 13

- **Тело ответа при отказе стоит печатать сразу.** Первая версия шага сообщала только HTTP-код — 403 объяснялся тремя разными причинами одинаково хорошо, и каждый прогон-гипотеза стоил полного деплоя.
- **Адрес API КАРМАНа держим в `secrets.SECRETS_VAULT_URL`, а не в файле** (D-038). У образца-донора он вписан литералом как fallback, а сама переменная нигде не задаётся.
- **`\n` в `curl -w` не переживает генерацию YAML скриптом** — надёжнее `-o файл -w '%{http_code}'`.
- **jq-выражения проверяемы без раннера:** на dev-машине и на боксе jq нет, на jump-host'е есть.
- **Слепой контроль — главная находка сессии, трижды за день.** Ошибался не проверяемый код, а сама проверка. Общее правило: **прежде чем поверить проверке, покажи, что она умеет и находить, и не находить**.
- **Проверка «в выводе ничего нет» на здоровом объекте проходит вакуумно.** Доказывать надо саму функцию редакции на входе, где опасные формы есть заведомо.
